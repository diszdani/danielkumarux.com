Section 1 · Opening and Product Context

An internal tool built for three different operational questions about the same data

The Archon Billing System is an internal operational tool built for Platform 3 Solutions to manage client billing and consumption across the Archon platform. It sits behind the product, not in front of customers. The people who use it daily are internal teams (Sales, Finance, and product team heads), each arriving with a different question about the same underlying data.

Sales wants to know where a client stands against what it purchased. Finance wants to know which consumption figures are relevant to a specific billing cycle. Product team heads want to understand how capacity is being used across the client base.

The same entitlement data has to serve all three. That was the design problem.

Section 2 · Users, Roles and the Design Challenge

Three teams, one entitlement model, three different operational priorities

The tool serves three internal user groups.

Sales tracks client standing relative to purchased entitlements. Their primary question is whether a client is approaching, within, or over what it bought. They need to interpret consumption figures quickly, usually in the context of a client conversation.

Finance works within billing periods. Their concern is not the full consumption picture but the consumption figures that are relevant to a specific billing cycle.

Product team heads want to understand how capacity is being used across the client base.

Each group shares access to the same interface. The design challenge was not to build three separate views. It was to structure the information so that each team’s question could be answered from a shared set of screens, without forcing any team to filter through data it did not need to reach what it did.

The additional complexity: the entitlement model is not simple. Archon tracks two independent tier structures, a data tier and a usage tier, each with its own limits across multiple dimensions. Neither is a subset of the other. Any interface that collapsed them or treated them as a single table would misrepresent how the product is actually licensed and billed.

Section 3 · Key Design Decisions

Four decisions that reflect the billing model, not just the billing screens

Before designing any screen, the work started with understanding the business rules that govern what numbers mean in this context. Four rules shaped the interface directly.

Decision 1

Make the entitlement model the foundation of the information architecture

The billing model is built around purchased entitlements. Every usage figure only makes sense relative to the allowance it was purchased against. Showing consumption without allowance creates the wrong interpretation: a number without its ceiling.

The interface follows the same logic. Wherever consumption is displayed, the purchased allowance accompanies it. Current consumption and purchased allowance are shown together for direct comparison, not on separate screens or in separate columns that require the user to hold one in memory while reading the other.

This was an information design decision before it was a visual one.

Decision 2

Separate the data tier and usage tier

The two entitlement models are independent. An interface that merges them into a single table would obscure this distinction. Users working in Finance or Sales need to see the two tiers as the product treats them: distinct, parallel, and individually complete.

The tier plan screen shows two separate matrices. Each has its own CURRENT badge marking the active tier. The separation is structural, not stylistic.

Decision 3

Anchor all figures to a billing period

A consumption figure without a period is ambiguous. The same number means different things depending on whether it represents a full month, a partial billing cycle, or a historical snapshot.

The billing period was placed above the consumption data, not beside it or in a metadata footer. It frames the figures before the user reads them. Keeping the billing period visible gives users the context they need to interpret consumption figures and distinguish the current period from historical data.

Decision 4

Place alert configuration in context, not in a separate settings area

Alerts are configured against entitlement limits. A threshold that is defined without reference to those limits is harder to reason about. A user setting a warning threshold needs to see the tier values at the same time.

The alert configuration panel opens as an overlay on the tier plan screen. The tier data remains visible in the background while the user sets thresholds, selects severity levels (warning or critical), assigns recipients, and sets a repeat percentage. The configuration and the data it references occupy the same view.

This was directly informed by watching how users approached the original alert setup process: they navigated away from tier data to find the alerts area, then had to remember the numbers they needed.

Section 4 · Key Workflows

Workflows designed around how each team moves through the tool

Workflow 1

Client selection and persistent context

The tool manages multiple clients. Any session begins with selecting a client, and that selection needs to persist throughout the session so that every figure the user reads is unambiguously tied to the right account.

The client selector sits in the page header. Once a client is selected, it is inherited across all client-specific views without requiring re-selection as the user moves between screens. The navigation is split across two scopes:

  • The global sidebar handles top-level modules: Dashboard, Clients, Plans, and Billing. These exist independently of any single client.
  • The client-specific tab bar handles the views that belong to a selected client: Dashboard, Tier Plan, and Billing.

The two scopes are visually and structurally distinct. The sidebar is always present. The tab bar only appears when a client context is active.

Workflow 2

The consumption dashboard

The dashboard answers the first question most users have when they open a client record: where does this client stand right now?

The information hierarchy follows a “position first, then direction” structure. For each dimension, the dashboard shows current consumption alongside purchased allowance for direct comparison, the current tier, and the percentage change versus the previous period. Separate trend charts for storage and query usage provide directional context below the summary data.

This ordering was deliberate. A user who opens the dashboard in a client conversation needs to know the client’s position before they can interpret movement. The reverse order, leading with trends and expecting the user to construct a summary, requires more effort and introduces more opportunity for misreading.

Workflow 3

Tier plan and alert configuration

The tier plan view is the reference screen for entitlement detail. It shows both tier matrices (data and usage) with the active tier marked on each. Users read this screen to understand what is contracted, not what is consumed.

Alert configuration is initiated from this screen. When a user opens the alert configuration panel, the tier data remains visible behind the panel. The user sets:

  • A threshold expressed as a percentage of the relevant limit
  • A severity level: warning or critical
  • One or more recipients
  • A repeat percentage for notifications

One implementation finding from the review: listing recipients in full made the panel unnecessarily long, so recipients were presented in an accordion that users could expand when needed. This keeps the panel compact without hiding recipient information.

Section 5 · Design System and Process

Shared components, adapted for a billing context

The Archon Billing System was designed within the same design system used across the Archon platform. The visual and component language is consistent: header context strip, sidebar navigation, tab bars, data tables, panels, and accordions. Users who work across Archon products move into the billing tool without relearning the interface.

The process followed a familiar pattern for internal tools: stakeholder conversations to establish the business rules, information modelling, then wireframing and design, with layout and component decisions tied to specific usage behaviours rather than to visual preference. The designs were handed off to engineering in Figma, and the implemented and deployed features then went through a UX review, with UX issues tracked and resolved through that review.

The implementation review, carried out after handoff and implementation, produced one concrete change: the recipients accordion, which addressed a panel height problem identified during the review rather than in earlier design phases. This kind of late-stage finding is normal. The review process exists to catch exactly this category of issue.

The tool brings together client management, consumption dashboards, tier plans, alert configuration, and billing. These areas were designed as a coherent system, with consistent navigation, shared contextual headers, and a unified approach to how data is labelled and scoped by period.

Section 6 · Outcomes and Reflection

What the tool delivered, and what good internal UX means in this context

The Archon Billing System shipped.

Quantified results were not captured, so none are claimed.

Reflection

Three things this project reinforced:

  1. 01

    Relate the concepts before designing the screens.

    The billing model (two independent tier structures, usage measured against purchased allowances, figures that belong to a period) had to be understood precisely before any screen was drawn. Getting the information model right made every layout decision easier and more defensible.

  2. 02

    Show the context that gives a number its meaning.

    A usage figure without its allowance is incomplete. A consumption snapshot without its billing period is ambiguous. The design keeps these pairs together so users can interpret data immediately, without reconstructing context from memory or additional clicks.

  3. 03

    Optimise internal tools for fast interpretation and clear operational decisions.

    Internal users are not casual. They return to these screens repeatedly, often in time-sensitive situations. The measure of a successful internal tool is not how pleasant it is on first use but how quickly and confidently experienced users can answer the question they came with.

The tool shipped. Quantified results were not captured, so none are claimed.
